# Coolify production configuration — platform implementation

Execution `/root/analysis_backend`, canonical platform-engineer; sequential implementation/self-review, not independent approval. Read AGENTS.md, workflow and platform role. Consulted official Coolify Git Compose and Service Compose documentation (https://coolify.io/docs/applications/builds/docker-compose and https://coolify.io/docs/services/configuration/docker-compose) for generated alphanumeric SERVICE_PASSWORD_64_ID/SERVICE_USER_ID values and Compose support.

Scope is infrastructure only: production Compose, nginx configuration, isolated production smoke and additive CI workflow. No React/application/auth/domain source, Dockerfile or existing quality/integration workflow changed.

Six services use existing web/API/worker image targets, PostgreSQL17, Redis7 with AOF/noeviction/password, SeaweedFS4.48 mini with generated S3 credentials and automatic private bucket. No host ports. Web exposes8080 for Coolify; api/web share the application network. Data network is internal and contains PostgreSQL/Redis/storage/worker; API also has application-network egress for authenticated SMTPS465. Fixed internal DNS api:3000 matches nginx. Three named volumes preserve data. API/worker/web drop capabilities and forbid privilege escalation; Redis runs as its image-owned redis user despite the shell-expanded password command. Runtime memory/CPU/PID limits are bounded; Redis maxmemory96mb is below its256MiB container limit to reserve persistence overhead. Capacity remains a pilot baseline, not measured production sizing.

API performs direct Prisma migrate deploy before exec; web/worker depend on API readiness and databases have healthchecks. Required variables fail Compose interpolation; production app validators additionally reject insecure origins/weak secrets/SMTP. Coolify supplies stable generated PostgreSQL/Redis/auth/storage secrets; user supplies APP_URL and SMTP host/user/password/from. S3 bucket is reconcile-documents. nginx accepts11MiB request envelopes while API preserves10MiB PDF limit, and blocks public operational-health endpoints.

Additive CI builds all three real targets sequentially and boots the complete Compose stack. Explicit CI-only synthetic guard protects the smoke from accidental normal execution. Smoke checks frontend HTML, same-origin API proxy, private readiness, cookie Secure/HttpOnly/SameSite, hostile origin rejection, completed migrations, authorized private S3 vs anonymous denial, synthetic verified login without email, real valid PDF greater than1MiB through nginx/private upload/actual worker extraction/bytehash download, platform queue ping, and logout. Container teardown/recreation without removing volumes then verifies PostgreSQL/Redis/S3 and uploaded PDF persistence and cleans synthetic state. No SMTP delivery is attempted or claimed; TLS/DNS/Coolify proxy deployment remain actual-server validation.

Local checks: smoke node --check and ESLint passed, owned YAML/JS formatter passed, git diff --check passed. Executor has no Docker daemon; actual image builds, Compose validation and production runtime acceptance await the new CI workflow. No local or remote deployment is claimed. Independent architecture and QA review and actual CI determine verification closure.
