# Reviewed claims — backend implementation

Execution `/root/analysis_backend`; backend/data implementation, sequential self-review, not independent approval. Scope: claims contracts/application/API routes, application wiring and analysis input collector export, Prisma schema and claims migration, actual HTTP claims integration suite.

Implemented append-only finding decisions with actor/reason/time/ordinal and separate operation reviewVersion; decisions do not change input fingerprints. Current verified writer, exact Origin, rate limit, private no-store, bounded input, tenant composite relationships and PostgreSQL row locks govern writes. Financial claim amounts originate only from persisted findings. Positive confirmed supported service/price differences produce correction requests; explicitly allowed incomplete comparisons produce clarification without requested amount. Arithmetic, tax, operation mismatch and matched outcomes cannot create automatic financial demands. Source must be a real invoice in the immutable run snapshot.

MVP deduplicates one claim per operation/invoice document. Explicit rebase is allowed only before sending, verifies the current confirmed review and same invoice, and appends source/draft versions while preserving earlier versions. Claim source captures run/parser/rule versions, source checksums, correction/extraction provenance, original filenames/invoice references, immutable findings/snapshot and human decision. Draft text is separately editable and versioned. Original PDFs remain behind authorized download routes.

Text and JSON exports require current evidence and unchanged confirmation. Exports persist exact bytes, SHA-256, actor/time/draft/source/version; authorized readers can download retained exports without changing status. Export never sends email. Draft/exported states may transition to manually recorded sent only with recipient confirmation; response/follow-up/resolution dates cannot be future or precede claim creation/latest business event. Follow-up requires due date; resolution requires outcome and reason. No recovered-money totals, payments, automatic email, accounting writes or external LLM exist.

Bounds: 100 claim versions, 10 source versions, 100 claims per operation, 1000 review ordinals; 512 KiB exports. Review summaries query current fingerprints without loading source histories. Claim mutations lock the claim row as well as the operation, preserving 409 concurrency semantics under Repeatable Read.

Four actual HTTP acceptance groups use real identity, PostgreSQL, uploaded PDF bytes, real extraction, actual deterministic analysis and private S3: 62 USD correction; confirmation prerequisite; no duplicate claim; editable/versioned draft; edit/edit and edit/export conflicts; immutable retained export bytes/hash/provenance; export distinct from sent; manual follow-up/resolution and dates; stale export/reversal rejection and explicit rebase; clarification with no amount; tenant/viewer/revoked membership/Origin; decision concurrency; forbidden client amount; arithmetic/tax/operation-mismatch exclusions. Tests are implemented here and reviewed independently by QA; they are not declared executed before CI.

Validation during implementation: Prisma generated and migration diff generated successfully; contracts/database/application/API strict builds and API integration test typecheck passed; changed-file ESLint passed; owned files formatted. Canonical check and real service integration remain coordinator/CI evidence. Independent architecture and QA records determine closure; this implementation record does not certify itself.

RC-R1 follow-up: root identified that source fingerprints alone did not expose changed human confirmation as stale. Claim detail now checks the latest exact organization/operation/run/finding decision ID and action against the captured confirmation. Review summaries perform the same check with bounded scalar JSON fields and a lateral latest-decision query, without loading source histories. The existing second HTTP group now asserts dismiss and reconfirm both remain stale in summary/detail, an explicit rebase on the same run restores freshness/export eligibility while preserving prior source/draft versions, and a later rebase onto a new run preserves all three source versions. Strict application/API test types and changed-file ESLint passed; actual runtime acceptance awaits the next CI candidate. No frontend contract or financial-rule changes were made.
