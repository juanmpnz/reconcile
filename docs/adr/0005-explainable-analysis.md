# ADR 0005 — replayable evidence-based logistics comparison

Status: accepted implementation contract; delivery and verification tracked separately. Date: 2026-10-15. Architecture/security/data/integration planning: `/root/analysis_architecture`; product/domain contract: `/root/analysis_product_domain`; backend ownership: `/root/analysis_backend`.

## Scope and dependency boundaries

Phase 3 compares explicitly associated documents within an operation. It distinguishes applicable external agreement, invoiced service and operational performance. A detected difference is a review finding, never accounting approval, confirmed recovery, an automatically sent claim or proof of fraud. Phase 4 human claim drafting and Phase 5 deployment/restore remain separate work.

Retain the modular monolith and ADR 0004's bounded application/Prisma tradeoff. Put typed deterministic comparison in the domain/sector-rules boundary without Nest, Prisma, queue or parser dependencies. Parse candidate facts from actual persisted extraction page text in the document-processing adapter. The application assembles snapshots, enforces authorization and persists them; the worker executes the same versioned pure rules. Do not create a universal rule DSL, an ERP adapter or hidden fixture lookup.

The backend owns shared Zod transport contracts. Product/domain owns pure comparison types and acceptance; agree those interfaces before dependent implementation. Explicit null/unknown and source evidence replace guessed defaults. Decimal strings cross HTTP and persistence JSON boundaries; decimal arithmetic performs calculations. No number-based monetary arithmetic, implicit FX or global tolerance.

## Operations and reviewed source facts

An operation belongs to one organization and has an explicit bounded reference. Operators choose documents through a tenant-scoped association; reference similarity may suggest a match but never authorizes access or silently establishes that services are identical. Every association uses composite organization/document and organization/operation constraints. Reads and writes verify the current verified member; owner/admin/analyst may write and viewer may read. Foreign and missing resources return a non-disclosing not-found result.

The structured adapter derives invoice lines, agreement conditions and operational facts from actual extraction pages, with document ID, extraction run/version, one-based page and bounded snippet. Supported fields include provider/reference, service/date/route, quantity/unit/unit price/line amount, currency/tax/total, agreement acceptance/estimate and validity, exclusions and performed-service identity. Missing or ambiguous facts remain unknown. Known fixture answers, filenames and expected-results are not inputs to the parser or rule engine. A parser optimized for explicitly documented demo labels is a bounded supported format, not general document intelligence.

Existing six-field document corrections must be applied consistently when deriving effective structured facts: latest correction for the selected extraction run wins, including explicit null. Preserve the original extracted values and evidence. Further structured corrections are append-only reviewed revisions with actor, reason, monotonic operation ordinal and source lineage; manual values must not be represented as automatically extracted evidence. Inputs include an optimistic revision token so a stale screen cannot overwrite newer review. A fresh extraction invalidates earlier derived candidates/reviews rather than silently rebasing corrections to new evidence.

## Snapshot and replay invariants

Create an immutable input snapshot when requesting an analysis, using a consistent PostgreSQL transaction and explicit document association/fact revisions. It contains the operation identity/reference, associated document IDs/checksums/kinds, exact extraction run IDs/versions, effective correction revisions, structured review revisions, parser version and rule version. Store normalized values and evidence in the snapshot, with immutable source provenance and input warnings alongside it in the run; a worker must not reread mutable current values to change a queued run's inputs.

A completed result includes per-line expected/invoiced/difference values, currency, rule identifier/version, evidence and a reason or missing condition. Separate the strength of documented support (confirmed/probable/not verifiable) from any human approval. Matching totals cannot suppress compensating line differences. Unknown service identity never equals another unknown identity. An estimate alone cannot establish an agreed price, expired/conflicting agreements cannot be silently selected, and differing currencies/taxes cannot be mixed into a claimed recoverable amount.

A completed run's snapshot and result are immutable. Document, association or review changes mark prior runs historical/stale when compared with their captured revision fingerprint; they never rewrite earlier conclusions. Re-execution produces a new run and version while retaining all prior runs. Identical request retries are idempotent for the same operation/input fingerprint/rule version; a deliberate new analysis remains distinguishable from duplicate HTTP delivery. The bounded MVP accepts at most 20 documents per operation, 100 lines per document and 16 KiB of normalized facts per document. Unsupported or oversized facts are omitted with an explicit input warning, never truncated into a purportedly complete invoice. Serialized run input and output each have a 128 KiB limit; an over-limit result fails without persisting that result. Operations expose the latest five full runs plus paginated metadata history and authorized single-run detail. At most 1,000 runs and 1,000 structured review revisions are accepted per operation; metadata exposes the latest 100 review revisions. Mutation requests are limited to 100 per actor per minute. These limits bound assembly, comparison and responses; they are pilot capacity limits rather than performance guarantees.

## Durable execution and authorization

Reuse the document pipeline's transactional PostgreSQL outbox and BullMQ delivery pattern. Persist the run, immutable snapshot and durable intent atomically. Queue payloads contain only identifiers. Validate job payload against persisted outbox/run/organization/operation/actor relationships; never trust tenant data from Redis. Recheck the initiating actor's current verified write membership before work and at commit; revoked access produces a visible blocked run without publishing business output.

Claim a run through an atomic bounded lease with a fresh fencing token, and commit only while owning the unexpired current lease. Terminal runs are no-ops on duplicate delivery. Retry infrastructure failures with bounded attempts/backoff and safe codes; do not overwrite terminal snapshots/results. The dispatcher reconciles unpublished intents, lost Redis jobs and stale leases, including jobs marked completed by Redis before PostgreSQL completion. Recovery may not duplicate results or allow an expired worker to overwrite a successor. Preserve the existing platform queue/smoke and document queue behavior.

All routes enforce existing exact Origin/Fetch Metadata policy for writes, verified sessions and fresh resource authorization. Private operation/fact/run responses use `Cache-Control: no-store`; queries are keyed by user/organization/resource and gated by fresh organization access. Do not expose object keys, confidential page text in logs, secrets, arbitrary URLs or unrestricted parser actions. Evidence is escaped text and authorized original download remains the ADR 0004 flow.

## Required verification and limits

Pure rule cases cover the 62 USD same-service discrepancy with complete agreement/operational evidence, matching invoice, missing/expired/estimated/conflicting agreement, different routes or service references, incomplete identity, unknown charge, compensating lines, decimal precision, currency mismatch, tax and unsupported rounding. Findings must not infer performance solely from a matching price.

Actual PostgreSQL/API/worker acceptance must cover association and fact/run tenant isolation, viewer and revoked access, Origin rejection, current scalar corrections, stale optimistic revisions, immutable historical replay, queued-snapshot isolation from later edits, duplicate delivery, invalid job tenant/actor payload, fencing and lost-job recovery. At least one positive end-to-end case must derive normalized facts from actual synthetic PDF text rather than manually injected engine answers. Browser fixtures can verify interaction and accessibility but cannot certify extraction, auth or real queue reliability.

No real CargoWise/Bravo Tran connection, arbitrary-format extraction, OCR/LLM generalization, company-validated accuracy, automated claim sending or production readiness is implied. Before a server demo complete deploy configuration, private storage, HTTPS/secrets, resource limits, backup/restore and deployed end-to-end verification; real confidential-data pilots retain prior MFA/security prerequisites.
