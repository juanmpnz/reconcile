# ADR 0006 — reviewed decisions, claim drafts and manual follow-up

Status: accepted prior implementation contract; delivery and verification tracked separately. Date: 2026-10-15. Architecture/security/data/integration: `/root/analysis_architecture`; product/logistics: `/root/analysis_product_domain`; backend owner: `/root/analysis_backend`. Delivery/verification tracked separately.

## Boundary and safety meaning

Phase 4 adds explicit human decisions to immutable analysis findings, editable claim drafts, authorized downloadable text/evidence exports and manually recorded follow-up. It does not send mail, validate destination ownership, change accounting state, make payments or equate a claimed amount with recovered money. Exported, manually sent and resolved are separate facts. Existing document/original download, extraction, rules and durable analysis jobs retain ADRs 0004/0005.

No new external integration or AI call is needed. Draft generation is deterministic from reviewed persisted evidence, not an invented recipient, contract, service or invoice field. Use no new dependency merely to generate an accessible text download and JSON dossier. Application services may retain the accepted direct Prisma tradeoff; financial calculations use Decimal and decimal string transport.

## Authorization and HTTP contracts

All resources remain scoped to organization and operation, with composite tenant foreign keys for decisions, claims and their run/revision/event relationships. Owner/admin/analyst can decide, create/edit claims and record follow-up/export events. Viewer can read existing decisions, drafts and history but cannot mutate. A current verified member check is mandatory in every use case, independent of browser capabilities and active organization. Foreign/missing resources use non-disclosing not-found responses.

Reuse exact Origin/Fetch Metadata checks, mutation throttling, bounded request bodies, validated schemas, private no-store responses and safe errors. Downloads require authorization before constructing the attachment; filenames are server generated, content types fixed, `nosniff` set and object keys/secrets omitted. No public link, HTML injection, arbitrary remote fetch or embedded active PDF is introduced.

Proposed shared transport owned by backend:

- `GET /operations/:operationId/review` exposes bounded decisions/claims and current review version/capabilities.
- `POST /operations/:operationId/analyses/:runId/decisions` receives finding index, confirm/accept/dismiss, bounded reason, expected review version and current input fingerprint. Confirm means the human supports pursuing the documented finding; accept means accepting the difference with reason; dismiss means rejecting the finding with reason. None approves payment.
- `POST /operations/:operationId/claims` receives run/finding identity and optimistic review version/fingerprint; the server chooses correction versus clarification and all financial/source fields.
- `PATCH /operations/:operationId/claims/:claimId` receives expected claim version and bounded recipient email, subject and plain-text body. It cannot modify source run/finding, claimed amount, currency or evidence.
- `POST /operations/:operationId/claims/:claimId/rebase` explicitly updates an unsent draft to a newly reviewed current finding of the same invoice, with expected claim/review versions, current fingerprint, run/finding and reason.
- `POST /operations/:operationId/claims/:claimId/events` records explicit bounded manual workflow events with expected version and required event-specific dates/reasons.
- `POST /operations/:operationId/claims/:claimId/export` receives expected version and text/dossier format. It verifies current decision/input eligibility and appends an export event atomically. As this records a mutation, it requires a writer; viewer historical reading remains separate.

Exact Zod DTO names and safe conflict codes are finalized with backend before frontend consumes them. A claim mutation conflict retains the user's draft for explicit review/retry; never silently overwrite a newer revision.

## Immutable decisions and concurrency

A decision is append-only and references exact organization/operation/run/finding index, actor, timestamp and reason. Validate that the run is completed and the index exists in its immutable result. For a new actionable decision or claim/export, require the captured run input fingerprint to equal the current operation fingerprint; do not pursue obsolete evidence by default. Historical decisions and dossiers remain readable without pretending they are current.

Serialize operation review changes with the existing operation row lock, current membership, expected review counter and input fingerprint in one transaction. Claim mutations also lock the tenant-scoped claim row, so RepeatableRead contenders cannot commit against an older claim snapshot or leak unique-version conflicts as generic failures. Do not increment the analysis input revision merely because a human decision or claim changed: that would make its own source run stale. Use a separate reviewVersion counter. Analysis requests, metadata/link/fact changes already serialize on the same operation row; cross-check current inputs inside the transaction. Claim revision/event writes additionally compare and increment their own claim version. Map PostgreSQL/Prisma serialization conflicts to safe 409 rather than service success.

Preserve decisions, draft revisions and events rather than overwriting history. Audit each real action atomically through the existing audit details field with identifiers, versions and bounded action metadata, avoiding duplicate copies of entire documents. No-op changes should not fabricate revision events. Terminal transitions are explicit and require reasons; historical timestamps do not replace server recordedAt/actor timestamps.

## Financial eligibility and deduplication

A correction requires the latest human decision to confirm the selected finding, documented confirmed support, a positive decimal difference and an eligible service-price/exclusion rule. Do not monetize arithmetic inconsistency, taxes, missing currency conversion, negative differences or undocumented assumptions. A clarification may pursue incomplete/probable support, but its amount remains null; its wording requests information rather than asserting a debt. Server authoritative amount/currency/source are frozen at creation and never supplied by the browser. Copy the selected immutable finding difference after safe Decimal validation; this phase needs no new monetary calculator and never uses Number for money comparisons.

Use one selected finding per initial claim. Never sum several flags for the same line/document: a total mismatch, line mismatch and excluded-service flag may describe overlapping money. Cross-currency totals and recovered-money metrics are outside scope. Durable uniqueness must prevent creating duplicate claims when the same document is analyzed again; an idempotent create returns the existing claim rather than fabricating another financial request. Coordinator-approved grouping: unique organization/operation/invoice-document, because parser `line-N` identifiers alone are not persistent service identity. Other findings remain visible but a second claim for another line of that invoice is outside this bounded MVP. Repeated create returns the existing claim. An explicit rebase endpoint may attach a newer current run/finding from the same document only while draft/exported: require claim version, review version, current fingerprint and reason, append an immutable source version and regenerated draft revision, and return to draft. Never rewrite former source/draft versions or rebase sent/responded/terminal claims. A sent historical claim remains the one follow-up record; no duplicate claim bypass is allowed.

## Draft, export and manual lifecycle

Generate an editable subject/body and retain revision history with author/date/reason as applicable. Destination starts unset; never guess a supplier email. State starts drafted. Export creates an exported event but never sent. Text export is the current reviewed plain-text draft. JSON dossier is a versioned evidence envelope with claim and immutable financial source, source run snapshot/result, document identifiers/checksums/extraction and correction revisions, relevant finding/evidence, decision and draft/event history. Include explicit demo and capability limitations where applicable. Original PDFs remain separate authorized downloads, with no public persistent links. Preserve each exported attachment as an immutable private database artifact with its SHA-256, claim/source/draft versions, actor and exact export time. An authorized read-only historical download returns those same bytes, checks integrity and does not change sent/exported state; viewers may read these existing historical artifacts. Creating a new export remains a writer-only audited action.

Recording sent requires explicit manual confirmation of destination and actual sent date no later than now; the application does not claim transport delivery. Responded requires response date and bounded note. Resolution requires actual date, reason and explicit outcome (corrected, accepted, rejected or withdrawn); do not infer recovered amount or close merely because the provider is reviewing. Follow-up due date remains manual and produces an internal visible status only, not an automatic email. Product defines the allowed transition matrix, including whether resolved drafts can reopen; backend rejects invalid transitions.

Export must fail safely if the latest decision no longer supports pursuit or underlying inputs changed. Existing historical claim content remains readable and clearly marked stale; do not silently rewrite its amount or rebind its source to a new analysis.

## Bounds and acceptance

The pilot caps 100 claims per operation, 1,000 review actions, 100 total claim versions and 10 immutable source versions per claim. Thus bounded detail windows cover all permitted source/draft/event history rather than silently losing an earlier sent event. Operation claim summaries read scalar rows plus current source fingerprints without loading each claim history. Draft body is limited to 10,000 characters, subject to 200, reasons to 1,000 and recipient email to 254. An export is at most 512 KiB and shares the 100-per-minute actor mutation rate limit; its bytes and audit event commit atomically. Validate export size before committing an export event; no partial event should claim a failed export succeeded. Responses and exports must avoid secrets, object keys and unrelated tenant documents. Required tests cover real tenant/role/Origin boundaries, stale source and optimistic conflicts, decision reversal, duplicate reanalysis, selected-flag overlap avoidance, immutable revision history, meaningful lifecycle dates/outcomes, current-only export and safe downloadable content. Browser fixture tests do not establish real authorization or database correctness.

Production deployment, backup restoration, confidential-data MFA/retention controls and real company validation remain Phase 5/6. This ADR is a bounded contract, not evidence those controls or Phase 4 have shipped.
